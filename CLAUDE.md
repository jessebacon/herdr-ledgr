# ledgr

A Herdr desktop-app mod that puts a two-direction request ledger beside a linear agent conversation: questions you park while the agent is still talking, and asks the agent makes of you, both held outside the transcript and anchored to the passage they came from. Phase 2 adds a Branch action that forks a parked question into its own session with an honest manifest of what the branch knows. Phase 3 adds the rejoin ("confluence"): one approved message carried back to the end of the trunk. Pins keep passages of a reply verbatim, with no question yet, so a later question can carry them as its context into the trunk or a branch.

Thesis in one line: keep a linear trunk, make non-linearity cheap and visible around it, and let a branch return its result, never its transcript.

## The one rule that matters

**This repo is the source of truth. The live install is a copy.** Edit here, then run `./install.sh` (the maintainer's own machine: `./install.sh --yes --answers examples/personal-overlay/answers.local.json`, his real answers, gitignored). Never edit `~/.config/herdr-app/mods/ledgr`, `mods/ledgr-pane` or `mods/my-tabs` in place. If an agent did edit the live copy (it happens during a build), run `./sync-from-live.sh` once to pull the changes back (it pulls the overlay mods into `examples/personal-overlay/`), review the diff, and go back to editing here.

Why a copy and not a symlink: Herdr refuses any import that resolves outside a mod's own folder, symlinks included, and the Claude Code hooks (in `~/.claude/settings.json` and each other chosen config folder's, `~/.claude-work/settings.json` in the examples) and the MCP server (in each folder's `.claude.json`) are registered against the installed path.

## Architecture in eight lines

1. Claude Code hooks (SessionStart, UserPromptSubmit, Stop) run `mods/ledgr/bin/adapters/claude/*.sh`. They inherit `HC_TERMINAL_ID` from the Herdr shell, so they can map terminal to session id, transcript path, cwd and turn; SessionStart and UserPromptSubmit also read the terminal's Herdr space (one `hc get $HC_TERMINAL_ID --json`, 300 ms limit, `ledgr_map.herdr_space()`) and record it. In a space listed in `spaces.disabled` they go quiet: the record and the map are written, but no spool event, no instruction, no landing and no extraction (`asks-instruction-space-off.txt` once to a session switched off, the mode's wording once when it is on again). They exit 0 fast, print nothing to the model's context except the ledgr-asks instruction (SessionStart, once after a missed blocker, once after an `asks.handoff` change), and ignore child or subagent processes (`LEDGR_INNER`, owner-pid rule).
2. Everything that changes state is a JSON event dropped into `~/.config/herdr-app/ledgr-data/spool/` with an atomic write: hooks, the capture box, panel actions, and the MCP server (`bin/mcp/ledgr_mcp.py`). `bin/lib/ledgr_spool.py` is the contract and has no Claude-specific imports.
3. One writer applies the spool to `ledgr-data/store.json` (source of truth) and `snapshot.json` (what the extractor reads), then deletes the spool file. The writer runs in an always-shown host copy because a panel block's mod copy only starts when first shown: the `ledgr` host block (props `{view: "host"}`, role `host`), or a mod with an engine copy (the maintainer's `my-tabs`, role `my-tabs`). Hosts elect one holder of `shared("ledgr.writer")`; the panel is a reader of `store.json` and falls back to being the writer only if no host answers within 4 s. The detail dialog is a second reader: its own copy of the mod (`detail.js`), opened per item, that reads `store.json` and the turn files itself, posts spool events and never pings, claims or runs a writer; both extend `reader.js` `Reader`. Never claim or ping from `herdr-app check` (it shares the window's shared state on 0.1.13): `config.js` `liveHome()` guards it.
4. Asks are declared first (by the MCP tool `declare_asks` when registered, else by a block), extracted as the fallback. The SessionStart hook puts the ledgr-asks instruction for the `asks.handoff` mode (`bin/lib/asks-instruction-ledgr.txt` or `-both.txt`; `prose` prints none; `instruct_block` stays the master switch) into the session's context, so the agent declares a blocker or a needed decision with `declare_asks` (written to `ledgr-data/mcp/<session>/<turn>.json` and spooled at once) or, without the tool, a fenced `ledgr-asks` block (bullets; a JSON array is still read). Only what the user personally must do, decide, provide or review is declared: a wait on the agent's own subagents, tools, builds or tests is never an ask, even as "I need", and the extractor's prompt holds the same rule (2026-11-10). At Stop the turn file `turns/<sid>/<turn>.md` gets the whole turn's assistant text (every text block since the prompt, the final message last; the `.json` beside it keeps the final message the extractor reads), and the extractor emits `pending`, resolves the turn's message uuid, and settles the tool declaration (quotes checked against that whole text) or reads that block (no model call); only a reply with neither goes to `claude-haiku-5-5` with forced JSON output (provider seam: `anthropic`, `openai-compatible`, `cli`). A blocking ask only the model found marks the session, and its next real prompt carries the instruction once (`instruct_reinject`). Either way it emits `asks`. Asks close three ways besides the person's Done: the agent's `resolve_asks` (when the user's message answers or drops one; `resolvedBy: "agent"`), a landed confluence (`"branch"`), or an answer that took (an ask answered by an `[A3]` ref or the answer sheet becomes `resolved`, `resolvedBy: "answer"`, at that turn's `asks` event unless the reply raised it again). A session in a space where ledgr is off declares nothing: it gets the off text instead of the instruction, and the MCP server writes nothing and answers `off: true`. An adapter's job is the instruction and the turns (`bin/adapters/README.md`); everything else is agent-neutral. Every ask carries a `level` (blocking, needed, optional); `extract.threshold` in `config.json` (shipped default needed; the maintainer's live config says blocking) decides which are open rows that count on the chip, and the rest are kept as folded suggestions.
5. Capture (`cmd-j`, `mod.open:ledgr`) opens over a working pane, parks a question with one keystroke, and accepts a clipboard quote only if it matches the saved turn text or `hc read`.
6. A message meant for an agent's prompt (the answer sheet, one answer, a confluence) is staged on the clipboard, its pane focused, and then pasted with Herdr's `terminal.paste` (what ⌘V runs) once Herdr reports that terminal focused on two looks in a row with the clipboard unchanged (`nav.js` `stageIntoPrompt`, `ui.pasteIntoPrompt`, default on). Never into a terminal with no agent or an agent waiting on its own prompt, and never Enter: the person adds a word of their own and sends it. When the focus is not confirmed within 600 ms, or the switch is off, it stays clipboard plus focus, as Go to anchor, Copy for prompt, `/btw` and Ask for a conclusion always are. One door: `stageIntoPrompt` is called only by nav.js `stageMessage` (one paste at a time per copy, the words of what happened), which only `reader.js` `Reader.stage` calls; neither `panel.js` nor `detail.js` defines `stage`, and copy methods never stage (11 rules in `test_no_keystrokes.py`). The dialog stages while open and closes once the paste is decided, since closing an overlay cancels its tasks. ledgr sends no keystrokes to any terminal: never `hc send` (it presses Enter and would submit a draft already in the prompt), never `hc keys` (Go to anchor pressed `ctrl+o /` until 2026-11-06; ctrl+o toggles Claude's transcript viewer), never `terminal.search`. `bin/tests/test_no_keystrokes.py` and `test_nav.mjs` enforce it (`terminal.paste` only inside `stageIntoPrompt`, without arguments, after the focus check). A staged confluence or answer sheet starts with a marker line (`ledgr confluence <branch> <item>`, `ledgr answers <session>`); the trunk's UserPromptSubmit hook sees it land and emits `confluence_landed` / `answers_landed` (`bin/lib/ledgr_landing.py`, `mods/ledgr/confluence.js`), one event per message when a prompt holds several (`detect_all`). Every staged message ends with one empty line (`nav.js` `promptText`), so a second paste into the same prompt does not run into the first.
7. Pins (`docs/design/Pins.md`, `docs/build-notes/BUILD-NOTES-pins.md`). In the capture box, ⌘S (`mod:ledgr` `"cmd-s": "ledgr.pin"`; `pinning.js` `PIN_KEY` and `pinDraft`) writes a `pin` spool event: the copied passage (up to 4,000 characters, line breaks kept), the box's line as its note, and an anchor (turn plus passage hash, uuid when known, never a position) from where the passage was found: a saved turn, else the screen (`hc read`), else unverified on a second ⌘S within 5 s. The writer keeps pins in their own `pins` map in `store.json`, beside `items`, so nothing that reads items (chips, counts, `snapshot.json`, refs, the archive, Forget) ever sees one; each pin carries its session's `source`, and the panel's `pin_note`, `pin_archive`, `pin_restore`, `pin_delete` apply by pin id even after Forget. A parked question carries pins through the box's `capture` Request (`request.pins`, at most 12, validated). Ask here stages `confluence.js` `pinsMessage` (marker `ledgr pins <session> <item>`, each passage quoted with `> ` and its provenance) through the paste of line 6; the trunk's hook emits `pins_asked` (quoted lines land nothing and give no refs: `ledgr_map.prompt_refs`), the question shows sent and is answered at that turn's Stop, and each pin records `answeredIn`. In a branch, `branch.js` `preamble` quotes the pins, the manifest gains a Given row, more than 24,000 pinned characters refuse the branch, Conclude prefills one entry per pin, and a landed confluence records `answeredIn` via the branch. No MCP tool reads pins yet.
8. The list and the detail dialog (`docs/design/Detail.md`, `docs/build-notes/BUILD-NOTES-detail.md`). The panel draws one line per item, pin or branch from `listing.js` `rowModel` (glyph, handle, one pill, the text's first line, a state word); Done (hovered or cursor row), Paste answer (an answer is ready) and Promote (below the threshold) are its only buttons. A click gives the list the keyboard (`focus_handle`, no `focusable` in `mod.json`); ↑ ↓, PageUp/PageDown, Home/End move a cursor over every line a click acts on, Enter does what its click does, Space checks a pin, Esc clears. A click or Enter on a row opens the dialog: `openOverlay(detailing.js detailSpec(…))`, `{view: "detail", session, kind, id, open, sel, opener, demo}`, `kind: "dialog"`, 0.6 × 0.75, routed in `main.js` before `isCapture`. It shows the item whole (text, quote, the message with the passage marked, every section and action the expanded row had), its text selectable `TextView.markdown(…).selectable(true)` (the person's and pinned text escaped by `mdVerbatim`), and in the message and an ask's text and quote a clicked web link opens in the browser and a file path (`links.js` `linkify`, under `https://ledgr.invalid/path/…`) opens with `links.editor` from the record's folder or its git toplevel (`detail.js` `openLink`; `opener.js` holds the reading copies' only `exec`); one at a time (a second open closes the first; a sub-row retargets in place); Esc or a click outside closes it, drafts flushed and the Conclude text kept in its `localStorage`. It writes `shared("ledgr.detail")` `{open, closed}` on open and close; the panel draws the open row raised, and from the closed record restores the cursor, shows the dialog's last words, takes its typed answers, and takes the keyboard back (30 ms, again at 300 ms) or leaves it in the pane a message was pasted into. A pin opened from the lane or search opens in the shown session, so a question built from it parks there. Renderers in `views.js`; none of the five new modules is an engine file. The settings dialog (`settings.js`, `{view: "settings", opener, demo}`, routed beside detail) is a third reading copy that writes `config.json` only through `Reader.saveConfig` (`reader.js` `editConfig`: compare-and-swap, queued; the panel's threshold menu and space switch use it too) and shares `ledgr.detail` (kind "settings", no id) so one dialog is open at a time; every copy draws with `withScale(theme(), textScaleOf(cfg))` (`t.ts(n)`, `ui.textScale`; the host, the chip and the box read the writer's `shared("ledgr.ui").textScale`).

## Engine copies (keep in sync)

Because of the import rule, a host in another mod (the overlay's `my-tabs`) cannot import from `mods/ledgr/`. `install.sh` copies the engine files into `mods/<host>/ledgr/` for every mod that imports `./ledgr/…` and verifies they are identical; the panel warns on drift. The list is `ENGINE_FILES` in `mods/ledgr/writer.js` (the installer reads it from there). If the writer gains a module, add it there. The copies are generated and never in the repo. The public install needs none: the host block lives inside `mods/ledgr`.

## Constraints that are not negotiable

- ledgr is a Herdr mod. It never reaches outside Herdr's home and the chosen Claude config folders (`~/.claude`, any second one such as `~/.claude-work`, and their `.claude.json` for the MCP registration); the installer also keeps its state in `~/.local/state/ledgr` and reads `~/.local/bin` wrappers and shell start-up files to find config folders. No Things 3, no other applications, no outbound calls except the extraction provider (the MCP server makes none). The one exception: a link or path the person clicks in the detail dialog opens in the browser or the chosen editor, never on ledgr's own initiative. No keystrokes into any terminal, and never Enter; the only write into a terminal is `terminal.paste` after its focus is confirmed (`ui.pasteIntoPrompt`).
- Shipped Herdr mods and layouts are read-only; the installer patches only a personal layout (offering `layout.clone` first). The maintainer's layout is `layouts/custom.json`; Kolczyk replaces the spaces block there, leave it alone.
- `herdr-app check mods/<name>` must pass for every touched mod. `herdr-app shot` returns the last painted frame; an inactive window does not repaint, so a stale shot is not evidence of failure.
- Do not fork or exercise large live sessions in tests. Create a throwaway Claude session in a scratch directory and branch from that; close test panes; remove test items through the panel's own spool events, never by editing `store.json` by hand.
- Back up any live file you edit to `~/.local/state/ledgr/backup-<date>/` first.
- Python core, no Node. This machine has no Homebrew jq or curl; use `python3 -I`.
- Depth cap for branches is a default (`branch.maxDepth`, 2), not a law. Honor the config value.

## Vocabulary

trunk (the main linear session) · park (capture a question without sending it) · lane (pins on top, then your questions, then asks of you) · pin (a passage of an agent's reply kept verbatim with its anchor and provenance, with no question yet; it lives on, through Forget and past the transcript, and a question quotes pins as its context) · held (the panel staying on one session instead of following the focused pane; the header's hold control, "pinned" until 2026-11-07) · ask (something the agent needs you to decide or do) · anchor (session + turn + passage hash, uuid optional) · branch (a forked session born from a parked question) · manifest (what a branch knows and does not know) · confluence (the one message a branch returns to the trunk) · landing (the trunk's hook seeing a staged message submitted) · spool (the event inbox) · writer (the single process that applies it) · off (a space where ledgr does nothing: no instruction, no extraction, no chip, no capture) · list (the panel since 2026-11-10: one line per item, pin or branch) · dialog, or detail (the centered overlay that shows one item whole, its text selectable, with every action; its own copy of the mod, `detail.js`) · cursor (the list's keyboard position, an entry key; Enter does what a click on that line does).
